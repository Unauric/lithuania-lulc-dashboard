# Lithuania Land Cover & Hydrology Dashboard

An interactive dashboard comparing seven land-cover datasets over Lithuania
(2017–2025-ish, depending on the dataset), plus a basin-by-basin hydrology
tool that pulls live gauge readings from the Lithuanian Hydrometeorological
Service and shows them alongside each basin's land-cover trend. Built by
the Lithuanian Energy Institute (LEI).

**License:** this repository is proprietary — see [`LICENSE`](LICENSE).
The hosted dashboard is free to use for anyone; the source code is not
licensed for reuse outside LEI. Read that file before assuming otherwise.

---

## What's actually running here

This is a **static site** (plain HTML/CSS/JS — no build step, no
framework, no `npm install`) plus a **precomputed data layer** (CSV/JSON/
raster tiles produced ahead of time by a Python analysis pipeline, not
computed live in the browser). The one piece of genuinely live data is the
hydrology tab's water-gauge readings, which come from a public API at
request time.

```
Browser (dashboard/) ──fetch()──> outputs/*.{csv,json,geojson}   (same-origin, static)
                       ──fetch()──> rasters/**/*.{png,tif}         (same-origin, static)
                       ──fetch()──> api.meteo.lt hydro station data
                                     └─ via serve_dashboard.py (local dev)
                                     └─ via a Cloudflare Worker (production —
                                        see dashboard/cloudflare-worker/)
```

Everything under `outputs/` and `rasters/` (except GRPK — see below) was
generated once by the scripts in `analysis/` and committed as static
files. Nothing in the dashboard itself runs Python; the analysis pipeline
is a separate, offline step you re-run only when you want to refresh the
data (new year of imagery, a fixed bug in the analysis, etc.).

## Quick start (run it locally)

Requires only Python 3 (for the local dev server) — no other install step.

```
git clone <this repo>
cd lithuania-lulc-dashboard
python serve_dashboard.py
```

Then open **http://localhost:8000/dashboard/index.html**.

On Windows, double-click `start_dashboard.bat` instead — it starts (or
reuses) the same server and won't accidentally leave a plain
`python -m http.server` bound to the port instead (see the comment at the
top of `start_dashboard.ps1` for why that distinction matters: a plain
static server has no `/api/hydro/` route, so the hydrology tab would look
broken with no obvious error).

**Don't** use `python -m http.server` directly — it serves the static
files fine, but has no route for `/api/hydro/...`, so every hydrology
feature (station popups, the correlation charts) will silently fail.
`serve_dashboard.py` is a drop-in replacement that adds exactly that one
route; everything else behaves identically to the plain http.server.

## Data *not* included in this repo

Two things were deliberately left out — both documented here so nobody goes
looking for them and assumes they're missing by accident.

### GRPK raster tiles (8.46 GB)

`rasters/grpk/` is Lithuania's national cadastral land-cover layer
(GRPK/PLOTAI), used for the GRPK option in "Land coverage" and as one of
the reference datasets in "Validation." It's **8.46 GB across ~8,800
files** — every other dataset combined is under 750 MB, so this one
dataset alone would have blown past what a normal git repo (and GitHub
Pages, which recommends staying under 1 GB) can reasonably hold.

It's hosted separately on external object storage (see
[`grpk-hosting/README.md`](grpk-hosting/README.md) for the full setup —
Cloudflare R2 by default, but any S3-compatible bucket works) and
`app.js`'s `GRPK_RASTER_BASE_URL` constant points every `rasters/grpk/...`
reference there instead of at this repo's own `rasters/` folder. If GRPK
tiles aren't loading:
1. Check `GRPK_RASTER_BASE_URL` in `app.js` actually points at a live,
   publicly-readable bucket (see `grpk-hosting/README.md`'s verify step).
2. Regenerate the tiles yourself: `analysis/export_grpk_lithuania.py` →
   `analysis/export_grpk_tiles.py` → `analysis/apply_grpk_water_exclusion.py`
   → `analysis/apply_grpk_river_inclusion.py`, from the raw GRPK cadastre
   source (ask LEI's GIS team for access — it's not public open data).

### Raw source datasets

`analysis/*.py` reads raw source imagery/vectors that also aren't in this
repo (multi-GB each, and mostly re-downloadable from their original
publishers rather than worth duplicating here):

| Dataset | What it is | Where to get it |
|---|---|---|
| Esri 10m Annual LULC | Esri/Impact Observatory annual land cover | [Esri Living Atlas](https://livingatlas.arcgis.com/landcover/) |
| CORINE Land Cover | EU land-cover inventory | [Copernicus Land Monitoring Service](https://land.copernicus.eu/pan-european/corine-land-cover) |
| HILDA+ (incl. KNN/Esri-fill variants) | Global 1930–2018+ land-use reconstruction | [HILDA+ project page](https://www.wsl.ch/en/projects/hilda.html) |
| HYDE 3.4 | Historical land use, long time series | [HYDE (PBL)](https://www.pbl.nl/en/hyde) |
| LUH2 v2h | Land-Use Harmonization | [LUH2 project page](https://luh.umd.edu/) |
| LUCAS LUC | EU in-situ land-use/cover survey | [Eurostat LUCAS](https://ec.europa.eu/eurostat/web/lucas) |
| GRPK/PLOTAI cadastre | Lithuanian national cadastre | LEI-internal / national geoportal, not public |

Each `export_<dataset>_lithuania.py` script's own docstring says exactly
what raw file(s) it expects and where. Re-running the whole pipeline from
scratch means: download the raw source → run that dataset's `export_*.py`
→ run its `export_*_tiles.py` (for the ones that need map tiles) → run
`apply_*_water_exclusion.py` if it has one → run `compute_subbasin_zonal.py`
and `compute_validation_metrics.py` to refresh `outputs/`.

## How it's deployed

### The static site

Plain static hosting — GitHub Pages, or literally any web server, works.
`dashboard/app.js`'s `resolveDataFileUrl()` figures out the site's own
base path from the URL at load time (looking for a `dashboard/` path
segment), so `outputs/`, `rasters/`, and the two root-level JSON files
just need to stay siblings of `dashboard/` — the exact layout already in
this repo. Don't nest `dashboard/` any deeper or move `outputs/`/`rasters/`
without updating that function.

### The hydro API proxy

`api.meteo.lt` (the live water-gauge data source) sends no
`Access-Control-Allow-Origin` header, so a browser blocks the dashboard's
own JS from fetching it directly, from any origin. Locally,
`serve_dashboard.py` proxies it same-origin. A static host like GitHub
Pages can't run that Python script, so production instead goes through a
small Cloudflare Worker that does the identical job — see
[`dashboard/cloudflare-worker/README.md`](dashboard/cloudflare-worker/README.md)
for how it's deployed and how `app.js` picks between the two (`localhost`/
LAN → local proxy, anything else → the Worker).

### CARTO basemap tiles

The gray "Positron" basemap comes from CARTO, which requires a free API
key (`CARTO_API_KEY` near the top of `app.js`) since 2026 — anonymous
requests get a watermarked tile. That key is necessarily public (it's used
in a client-side `fetch()` URL, same as any browser-based map app) and
tied to a free-tier quota (5M tile requests/month) — if it ever needs
rotating (e.g. quota abuse from someone copying it elsewhere), get a new
one free at [carto.com/basemaps/apikey](https://carto.com/basemaps/apikey/)
and swap the constant.

## Key things to know before changing the hydrology tab

- **`SHOW_HYDRO_CORRELATION`** (near the top of the hydrology section in
  `app.js`) is currently `false`. The full correlation feature (Pearson/
  Spearman stats, verdict badges, the cross-basin pooled/meta-analysis
  view) is fully implemented and untouched behind this flag — it's off
  because the current product decision is to show a plain side-by-side
  land-cover/discharge comparison instead, not because the correlation
  code is broken or removed. Flip it back to `true` to restore the old
  behavior with no other changes needed.
- **`basin_hydrology_correlation.py`** picks one reference gauging station
  per basin automatically (most-downstream station on the basin's named
  river) and writes `outputs/basin_hydrology_correlation.json`, which the
  dashboard reads. If you add/change stations in `dashboard/
  hydro_stations.json`, you need to re-run this script for the pick to
  update — the dashboard doesn't re-derive it.
- **`dashboard/hydro_stations.json`** intentionally holds only ~20 of the
  ~97 real stations from api.meteo.lt (the ones actually used as basin
  references, plus a couple kept by request). The full station list isn't
  in this repo; if you need it back, api.meteo.lt's
  `/v1/hydro-stations` endpoint returns all of them directly.
- **Basin naming**: `dashboard/basins-config.json`'s `namesByObjectId` maps
  each of the 19 sub-basin polygons (by `OBJECTID` in `lt_subbasins.json`)
  to a display name. Several of these were originally mislabeled (verified
  by point-in-polygon against real towns) — if a basin's name and its
  polygon's real-world location ever look mismatched again, that's the
  file to check.
- Station names from api.meteo.lt come in as `"<Lithuanian place name> VMS"`
  (VMS = *Vandens matavimo stotis*, "water measurement station"). `app.js`'s
  `translateStationName()` rewrites the "VMS" suffix to "gauging station"
  once, at data-load time — don't hardcode " station" onto a name anywhere
  else, or you'll get "... gauging station station".
